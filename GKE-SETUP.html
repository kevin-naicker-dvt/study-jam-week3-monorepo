How this differs from Cloud Run

Same app, different hosting model

Topic Cloud Run (GCP-SETUP) GKE (this lab)
Workloads Managed revisions Pods, Deployments, Services
Networking VPC connector to Cloud SQL Cluster nodes in VPC reach Cloud SQL private IP
Public HTTP Cloud Run URLs Ingress (or LoadBalancer services)
Frontend VITE_API_URL Injected in Cloud Build from Run URL You choose a stable URL (Ingress hostname) before building the frontend image
Scaling Automatic HPA / cluster autoscaler (configurable)
DB_PASSWORD / JWT_SECRET gcloud run deploy --set-secrets maps Secret Manager → env vars You create a Kubernetes Secret in the cluster (e.g. studyjam-k8s-runtime); GKE does not read Secret Manager automatically unless you add CSI / External Secrets

The backend serves /health (no /api prefix) and /api/* for the API (backend/src/main.ts). The production frontend listens on 8080 (nginx); the backend on 3000.

Can you do this lab from the Google Cloud Console?

Yes, for almost everything — plus Cloud Shell when needed

Yes, for almost everything. You do not need gcloud or kubectl on your laptop if you use the Console plus Cloud Shell (Activate Cloud Shell in the header).

What Console / Cloud Shell?
Enable APIs, VPC firewall rules Console (APIs & Services, VPC Network)
Create / delete GKE cluster Console (Kubernetes Engine)
Connect kubectl to the cluster Console → cluster Connect → Run in Cloud Shell
Build container images No Docker build button in Console — reuse Artifact Registry images or Cloud Build
Namespace, Secrets, ConfigMaps Console (GKE → Configuration); sometimes one kubectl line in Cloud Shell
Deployments, Ingress, Jobs Deploy wizard for simple cases; Apply YAML / kubectl apply in Cloud Shell for this repo
Logs, Ingress IP, verify Console + browser; optional curl in Cloud Shell

“Limited gcloud” usually means: open Cloud Shell, run Connect once, then short kubectl commands or paste YAML.

Step 2 — Networking and Cloud SQL

Private IP reachability from the cluster

  1. Note the private IP of studyjam-db (Cloud SQL → instance → Overview / Connect).
  2. Create the cluster in africa-south1 on the default VPC so traffic can reach SQL.
  3. If connections time out, add a VPC firewall rule (VPC network → Firewall) for TCP 5432 from GKE subnets to Cloud SQL (tighten for production).

Verify (Cloud Shell is enough)

# Replace CLOUD_SQL_PRIVATE_IP with your instance private IP
kubectl run psql-test --rm -it --restart=Never --image=postgres:15-alpine -- \
  psql "postgresql://studyjam_user@CLOUD_SQL_PRIVATE_IP:5432/studyjam"

Use the password from Secret Manager when prompted. Exit with \q.

Step 3 — Create a GKE cluster

Console workflow + optional gcloud

Lab name: studyjam-k8s-v2 (Autopilot, africa-south1, default VPC). If your cluster name differs, substitute it in gcloud and Connect.

Create the cluster (Google Cloud Console)

  1. Kubernetes Engine → Clusters → Create
  2. Choose Autopilot (or Standard if required)
  3. Name studyjam-k8s-v2, region africa-south1
  4. Keep default VPC
  5. Create and wait until Running

Connect Cloud Shell (minimal CLI)

  1. Clusters list → Connect on studyjam-k8s-v2
  2. Run in Cloud Shell (runs gcloud ... get-credentials)
  3. kubectl get nodes should list nodes

Optional: gcloud

Autopilot

gcloud container clusters create-auto studyjam-k8s-v2 \
  --region=africa-south1 \
  --project=dvt-lab-devfest-2025 \
  --release-channel=regular

Standard

gcloud container clusters create studyjam-k8s-v2 \
  --region=africa-south1 \
  --project=dvt-lab-devfest-2025 \
  --num-nodes=2 \
  --machine-type=e2-medium \
  --enable-ip-alias \
  --release-channel=regular
gcloud container clusters get-credentials studyjam-k8s-v2 \
  --region=africa-south1 \
  --project=dvt-lab-devfest-2025

Step 4 — Build and push images

Artifact Registry paths

Console workflow (no local Docker)

  • Reuse images from Cloud Build / Cloud Run: Artifact Registry → studyjam-repo — use existing tags (e.g. :latest) in Deployments instead of :gke-latest.
  • New VITE_API_URL: rebuild the frontend via Cloud Build with the correct --build-arg.

Local Docker (optional)

gcloud auth configure-docker africa-south1-docker.pkg.dev

Backend

docker build -t africa-south1-docker.pkg.dev/dvt-lab-devfest-2025/studyjam-repo/studyjam-backend:gke-latest ./backend
docker push africa-south1-docker.pkg.dev/dvt-lab-devfest-2025/studyjam-repo/studyjam-backend:gke-latest

  --build-arg VITE_API_URL=https://studyjam.example.com/api \

docker push africa-south1-docker.pkg.dev/dvt-lab-devfest-2025/studyjam-repo/studyjam-frontend:gke-latest

Step 5 — Kubernetes secrets

DB password and JWT

⚠️

Why Cloud Run works but GKE needs this step

The same image expects DB_PASSWORD and JWT_SECRET in the environment. On Cloud Run, cloudbuild.yaml uses --set-secrets so GCP Secret Manager values are injected at deploy time. GKE does not do that — you must create a Kubernetes Secret (studyjam-k8s-runtime with those exact keys) in namespace studyjam-k8s, as below. Otherwise the backend may crash with JwtStrategy requires a secret or key. After updating the Secret, run kubectl rollout restart deployment/studyjam-k8s-be -n studyjam-k8s.

Google Cloud Console

GKE → cluster studyjam-k8s-v2 → Configuration → Secrets → Create. Namespace studyjam-k8s. Opaque secret studyjam-k8s-runtime with keys DB_PASSWORD and JWT_SECRET.

kubectl (Cloud Shell or local)

kubectl create namespace studyjam-k8s

kubectl create secret generic studyjam-k8s-runtime \
  --namespace=studyjam-k8s \
  --from-literal=DB_PASSWORD='YOUR_DB_PASSWORD' \
  --from-literal=JWT_SECRET='YOUR_JWT_SECRET'

From Secret Manager:

DB_PW=$(gcloud secrets versions access latest --secret=studyjam-db-password --project=dvt-lab-devfest-2025)
JWT=$(gcloud secrets versions access latest --secret=studyjam-jwt-secret --project=dvt-lab-devfest-2025)

kubectl create secret generic studyjam-k8s-runtime \
  --namespace=studyjam-k8s \
  --from-literal=DB_PASSWORD="$DB_PW" \
  --from-literal=JWT_SECRET="$JWT"

Runnable sync from a local env file (.env-style)

Placeholder file: backend/kubernetes/env/runtime-secrets.env.example. Copy to backend/kubernetes/env/runtime-secrets.env (gitignored), set real values for DB_PASSWORD and JWT_SECRET, then either:

./backend/kubernetes/job-apply-runtime-secret-from-env.sh
# or pass another path: ./backend/kubernetes/job-apply-runtime-secret-from-env.sh /path/to/.env
kubectl apply -k backend/kubernetes/secret-from-env

A Kubernetes Job manifest is not used here—secret literals in a Job spec would be visible in the API. The script pipes the same kubectl create secret … --dry-run pattern as above.

ℹ️

Production note

For production, prefer Workload Identity + Secret Manager CSI or External Secrets.

Secure secret workflow

  • Use Cloud Shell; prefer reading from Secret Manager (example above) over pasting passwords into chat or notes.
  • Never commit Secret YAML, production .env, or base64 dumps to Git.
  • Use kubectl create secret ... --dry-run=client -o yaml | kubectl apply -f - so plaintext does not sit in a file on disk.
  • Verify metadata only: kubectl get secret studyjam-k8s-runtime -n studyjam-k8s (expect DATA = 2); list key names with go-template in GKE-SETUP.md Step 5.
  • If you used the Console wizard, run kubectl set env deployment/studyjam-k8s-be -n studyjam-k8s --from=secret/studyjam-k8s-runtime when the Deployment lacked secretKeyRef.

Step 6 — ConfigMap

Non-sensitive backend environment

Using Kustomize (Step 7)? Edit backend/kubernetes/configmap.yaml and apply with kubectl apply -k backend/kubernetes instead of the imperative kubectl create configmap below if you prefer the repo file as source of truth.

Console: ConfigMaps → Create, name studyjam-k8s-backend-config, namespace studyjam-k8s.

KeyExample value
NODE_ENVproduction
PORT3000
DB_HOSTCloud SQL private IP
DB_PORT5432
DB_NAMEstudyjam
DB_USERstudyjam_user
FRONTEND_URLhttps://studyjam.example.com (must match browser origin)
 
kubectl create configmap studyjam-k8s-backend-config \
  --namespace=studyjam-k8s \
  --from-literal=NODE_ENV=production \
  --from-literal=PORT=3000 \
  --from-literal=DB_HOST=CLOUD_SQL_PRIVATE_IP \
  --from-literal=DB_PORT=5432 \
  --from-literal=DB_NAME=studyjam \
  --from-literal=DB_USER=studyjam_user \
  --from-literal=FRONTEND_URL=https://studyjam.example.com

Step 7 — Deploy workloads (Kustomize)

backend/kubernetes — GKE-friendly layout

Repo path: backend/kubernetes/. Uses Kustomize (kustomization.yaml), recommended app.kubernetes.io/* labels, one manifest per resource, namespace studyjam-k8s. Secrets are not in Git (create in Step 5). The migration Job is not in the default bundle — apply it separately (Step 9).

# Repo root; edit backend/kubernetes/configmap.yaml (DB_HOST, FRONTEND_URL) and ingress host if needed
kubectl apply -k backend/kubernetes
kubectl rollout status deployment/studyjam-k8s-be -n studyjam-k8s
kubectl rollout status deployment/studyjam-k8s-fe -n studyjam-k8s
kubectl get pods,svc,ingress -n studyjam-k8s

Preview: kubectl kustomize backend/kubernetes

Console wizard: Workloads → Deploy; attach both ConfigMap and Secret keys DB_PASSWORD, JWT_SECRET.

⚠️

ConfigMap only = CrashLoopBackOff

If the Deployment lacks secretKeyRef, run kubectl set env deployment/studyjam-k8s-be -n studyjam-k8s --from=secret/studyjam-k8s-runtime or apply from backend/kubernetes/deployment-backend.yaml.

Step 8 — Ingress IP and DNS

Included in kubectl apply -k backend/kubernetes

kubectl get ingress -n studyjam-k8s

Wait for ADDRESS; point spec.rules[0].host at that IP (DNS, /etc/hosts, or nip.io). Edit backend/kubernetes/ingress.yaml before apply if the host is not studyjam.example.com.

Step 9 — Database migrations (Job)

Apply once base stack is up

kubectl apply -f backend/kubernetes/job-migrate.yaml
kubectl logs -n studyjam-k8s job/studyjam-k8s-migrate -f

Expect Migrations complete. On failure: kubectl delete job studyjam-k8s-migrate -n studyjam-k8s, fix, re-apply.

Cost notes (approximate)

GKE vs Cloud Run

GKE Autopilot bills per pod resource requests; Standard bills for nodes plus cluster management. A small lab cluster plus Cloud SQL is usually more expensive than Cloud Run at low traffic. Delete the cluster when finished.
