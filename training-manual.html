🗺️

Project Overview

What we built and why each technology was chosen

This project builds and deploys a minimal but production-realistic 3-tier web application to GCP using an AI-assisted development workflow in Cursor IDE. The goal is to learn cloud deployment fundamentals by doing — including the mistakes.

⚛️

Frontend (UX)

ReactJS + Vite. Single-page app served by a containerised Nginx server on Cloud Run. The API URL is baked in at build time via VITE_API_URL.

🟢

Backend (API)

NestJS on Node.js 18. RESTful API with JWT authentication. Deployed independently and must pass a /health check before the frontend is built.

🗄️

Database

PostgreSQL 15 on Cloud SQL. Private IP only (no public exposure). Schema managed by Drizzle ORM migrations.

🔄

CI/CD Pipeline

GitHub push to gcp/dev triggers Cloud Build, which builds Docker images, runs health checks, and deploys both services to Cloud Run.

🔐

Secrets

DB password and JWT secret stored in GCP Secret Manager. Never in code, environment files, or build logs.

🛡️

IAM & Security

Two dedicated service accounts (one for build, one for runtime) following least-privilege principles. VPC connector for private Cloud SQL access.

Architecture

How data flows from a git push all the way to the database

GitHub Push → gcp/dev branch │ ▼ ┌─────────────────────────────────────────────┐ │ GCP Cloud Build │ │ │ │ Step 1: Build Backend Docker Image │ │ (includes migrate.js + drizzle/) │ │ Step 2: Push to Artifact Registry │ │ Step 3: Deploy studyjam-backend │ │ (with VPC connector attached) │ │ Step 4: Health check /health ──────────────┼──► 200 OK required │ Step 5: Get backend URL │ │ Step 6: Build Frontend Image │ │ (VITE_API_URL baked in) │ │ Step 7: Push to Artifact Registry │ │ Step 8: Deploy studyjam-frontend │ └─────────────────────────────────────────────┘ │ ├──► Cloud Run: studyjam-backend (port 3000) │ │ │ │ via VPC Connector (10.8.0.0/28) │ ▼ │ Cloud SQL: PostgreSQL (10.74.0.3:5432) │ Private IP only — no public exposure │ └──► Cloud Run: studyjam-frontend (port 8080) │ ▼ (user's browser) https://studyjam-frontend-xxx.run.app │ API calls → VITE_API_URL ▼ https://studyjam-backend-xxx.run.app/api
💡

Key Design Decision: Health Check Gate

The frontend is only built after the backend passes its health check. This ensures the VITE_API_URL injected into the frontend build always points to a live, healthy API endpoint.

Step 4 — Create VPC Connector

VPC network → Serverless VPC Access → Create Connector Required

🔴

This step is mandatory — do not skip it

Cloud SQL is configured with a private IP only. Cloud Run runs in a shared Google network and cannot reach private VPC addresses without a connector. Without this, every database query will timeout silently after ~127 seconds and return HTTP 500 to the user.

What happens in cloudbuild.yaml

The cloudbuild.yaml deploy step automatically attaches the connector using the _VPC_CONNECTOR substitution variable:

- '--vpc-connector=projects/$PROJECT_ID/locations/${_REGION}/connectors/${_VPC_CONNECTOR}'
- '--vpc-egress=private-ranges-only'

Step 9 — First Deployment

Push to gcp/dev → Cloud Build runs automatically

git add .
git commit -m "feat: initial deployment"
git push origin gcp/dev

Go to Cloud Build → History and watch the build. All 8 steps must go green. The backend health check (Step 4 in the pipeline) hits /health up to 10 times before failing — if it fails, check Cloud Run logs for startup errors.

⚠️

The app starts successfully but register/login will fail until migrations run

The backend will start and the health check will pass, but the users table doesn't exist yet. Any API call that touches the database will return HTTP 500. That's expected — proceed to Step 10.

🔟

Step 10 — Run Database Migrations

Cloud Run command override — creates the users table

🔴

VPC connector must be active first

If the migration revision can't reach Cloud SQL, it will silently timeout. Confirm the VPC connector status is Ready and that the _VPC_CONNECTOR substitution variable is set in the trigger before continuing.

How migrations work in this project

The Dockerfile compiles src/database/migrate.ts to dist/database/migrate.js and copies the drizzle/ SQL files into the image. This means the migration runner is always bundled with the deployed image — you just need to tell Cloud Run to run it instead of the normal server.

Running the migration via Cloud Run

Open Edit & Deploy New Revision

Cloud Run → studyjam-backend → Edit & Deploy New Revision

Set the command override — two separate fields

FieldValue
Container commandnode
Container argumentsdist/database/migrate.js
❌

Do NOT put both in the Container command field

Entering node dist/database/migrate.js as a single string in the command field causes Cloud Run to look for a binary literally named node dist/database/migrate.js, which fails with "no such file or directory". The command and argument must be in separate fields.

Deploy and watch the logs

Click Deploy. Go to Logs tab and wait for:

Running migrations...
Migrations complete.

The revision will be marked unhealthy afterwards (expected — the process exits after migration). That's fine.

Restore normal operation

Click Edit & Deploy New Revision again. Clear both fields (Container command and Container arguments). Click Deploy. The backend returns to serving the API normally.

Verify migrations succeeded

Open Cloud SQL → studyjam-db → Cloud SQL Studio and run:

SELECT * FROM drizzle_migrations;   -- should return 1 row

SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public';     -- should include 'users'

Lessons Learned

What went wrong, why, and how we fixed it

This deployment surfaced six distinct problems, each revealing something important about cloud infrastructure. These are documented here so future teams don't repeat the same journey.

1

VPC Connector Was Never Set Up

Critical

Symptom: Backend started successfully, health check passed, but every POST /api/auth/register returned HTTP 500 after exactly 127 seconds. No useful error message.

🔴 What happened

Cloud SQL was configured with a private IP only. Cloud Run runs in Google's shared infrastructure and cannot route to private VPC IPs without a connector. TCP connections to 10.74.0.3:5432 silently timed out. Drizzle ORM's error said "Failed query" which masked the real cause.

🟢 The fix

Create a Serverless VPC Access Connector (vpc-studyjam-connector, CIDR 10.8.0.0/28). Add --vpc-connector and --vpc-egress=private-ranges-only to the Cloud Run deploy command. Add _VPC_CONNECTOR as a build trigger substitution variable.

💡

Key takeaway

A 127-second timeout before a 500 error on database calls almost always means "Cloud Run cannot reach the database at all" — not "the database query failed". Check VPC connectivity before assuming a query bug.

2

migrate.ts Was Not Compiled Into the Docker Image

Build Issue

Symptom: Cloud Run command override failed immediately with "Cannot find module '/app/dist/database/migrate.js'".

🔴 What happened

nest build only compiles TypeScript files reachable from main.ts through the module import graph. migrate.ts is a standalone script — it's never imported by any module — so nest build silently excluded it from the output.

🟢 The fix

Add an explicit tsc compile step in the Dockerfile builder stage, after nest build, to compile migrate.ts independently into dist/database/migrate.js.

# In Dockerfile — after RUN npm run build:
RUN node_modules/.bin/tsc --module commonjs --target ES2021 \
    --moduleResolution node --esModuleInterop --skipLibCheck \
    --outDir dist --rootDir src src/database/migrate.ts
3

Drizzle Migrations Folder Was Missing From the Docker Image

Build Issue

Symptom: Cloud Build failed with "COPY failed: stat app/drizzle: file does not exist".

🔴 What happened

Two problems compounded: (1) the drizzle/ SQL migration files had never been generated locally (npm run db:generate had never been run), and (2) even when generated, the Dockerfile didn't copy them into the production image.

🟢 The fix

Add RUN npm run db:generate to the Dockerfile builder stage — this generates migrations from the schema at Docker build time, requiring no DB connection. Then add COPY --from=builder /app/drizzle ./drizzle to the production stage.

✅

Key takeaway

drizzle-kit generate only reads your schema.ts — it does not need a database connection. It can safely run during Docker build in CI/CD.

4

Wrong Cloud Run Command Override Format

Config Mistake

Symptom: Migration revision failed with "failed to load /app/node dist/database/migrate.js: no such file or directory". Notice the space in the path — the entire string was treated as a single binary name.

🔴 What happened

In the Cloud Run UI, node dist/database/migrate.js was entered as a single string in the Container command field. Cloud Run uses this as the ENTRYPOINT — it tried to find an executable literally named node dist/database/migrate.js.

🟢 The fix

Use two separate fields: Container command = node, Container arguments = dist/database/migrate.js. These map to Docker's ENTRYPOINT and CMD respectively.

5

Health Check Used Wrong URL Path

Config

Symptom: Cloud Build's health check step kept failing with 404, even though the backend was running.

🔴 What happened

The Cloud Build health check script was polling /health but the NestJS app registers all routes under the /api global prefix. The actual health endpoint is at /api/health.

🟢 The fix

Update the health check curl in cloudbuild.yaml to use the correct path: $$BACKEND_URL/health → $$BACKEND_URL/api/health.

6

PORT Environment Variable Conflict

Config

Symptom: Early Cloud Build runs failed at deploy time with: "The following reserved env names were provided: PORT. These values are automatically set by the system."

🔴 What happened

PORT is a reserved environment variable on Cloud Run — it sets the port the container must listen on. Attempting to set it manually via --set-env-vars in the gcloud run deploy command causes a validation error.

🟢 The fix

Remove PORT from the --set-env-vars list and use --port=3000 instead. The backend reads process.env.PORT which Cloud Run sets automatically at runtime.

Glossary

Key terms and concepts used throughout this project

Artifact Registry GCP
GCP's managed Docker image registry. Stores versioned container images tagged by commit SHA. Replaces the older Container Registry (gcr.io).
GCP Service
Cloud Build GCP
Serverless CI/CD pipeline service. Executes cloudbuild.yaml steps in managed Docker containers. Triggered by GitHub pushes via a Cloud Build Trigger.
GCP Service
Cloud Run GCP
Serverless container platform. Runs Docker images on-demand, scales to zero when idle. Each deployment creates a new immutable Revision.
GCP Service
Cloud SQL GCP
Managed relational database service. Used here as PostgreSQL 15 on db-f1-micro. Configured with private IP only — not accessible from the public internet.
GCP Service
cloudbuild.yaml
The CI/CD pipeline definition file. Declares ordered build steps, substitution variables, machine type, and timeout. Lives in the repo root and is executed by Cloud Build on each trigger.
Config File
CIDR Range
Classless Inter-Domain Routing — a notation for IP address ranges. 10.8.0.0/28 means 16 IP addresses starting at 10.8.0.0. Used for the VPC connector's dedicated subnet.
Networking
Container Command / Args
In Cloud Run, the Container command overrides Docker's ENTRYPOINT and the Container arguments override CMD. They are separate fields — not a single combined string.
Cloud Run
Drizzle ORM
TypeScript-first ORM for SQL databases. Uses a schema file (schema.ts) to generate type-safe SQL migrations via drizzle-kit generate. Migrations are plain SQL files stored in the drizzle/ folder.
Library
Drizzle Migration
A SQL file generated from schema changes. Applied to the database by running migrate.ts (or its compiled version migrate.js). Tracked in the drizzle_migrations table so each migration only runs once.
Database
Health Check
An HTTP request made to /health (or /api/health in this project) to verify the service is alive and ready to receive traffic. Cloud Build uses this as a gate before building the frontend.
Ops
IAM Identity and Access Management
GCP's permission system. Controls which service accounts (or users) can perform which actions on which resources. Follows the principle of least privilege — grant only what is needed.
GCP Service
JWT JSON Web Token
A compact, signed token used for stateless authentication. The backend signs tokens with a secret key stored in Secret Manager. The frontend includes the token in the Authorization header for protected routes.
Auth
Monorepo
A single Git repository containing multiple related projects. Here: frontend/ (React), backend/ (NestJS), and scripts/. One cloudbuild.yaml orchestrates both.
Architecture
Multi-stage Docker Build
A Dockerfile technique where a large "builder" image compiles the code, and a smaller "production" image copies only the compiled output. Reduces final image size and excludes dev tools from production.
Docker
NestJS
A structured Node.js framework for building server-side applications. Uses TypeScript, decorators, and a module system inspired by Angular. nest build compiles only files reachable from the app's module graph.
Framework
Private IP
An IP address only routable within a VPC network — not accessible from the public internet. Cloud SQL in this project is assigned a private IP (10.74.0.3). Cloud Run requires a VPC connector to reach it.
Networking
Revision (Cloud Run)
An immutable snapshot of a Cloud Run service configuration (image, env vars, resources). Each deploy creates a new revision. Traffic can be split across revisions. Failed revisions don't receive traffic.
Cloud Run
Secret Manager GCP
A service for storing encrypted credentials. Values are never stored in source code, Docker images, or build logs. Cloud Run accesses them via --set-secrets and injects them as environment variables at runtime.
GCP Service
Service Account
A non-human identity used by applications and services (not people). This project uses two: one for the CI/CD pipeline (cloudbuild-sa) and one for the running application (cloudrun-sa).
IAM
Serverless VPC Access Connector
A GCP resource that creates a bridge between Cloud Run (serverless, shared network) and a VPC (private network). Required whenever Cloud Run needs to reach resources with private IPs such as Cloud SQL.
Critical
Substitution Variables
Named placeholders in cloudbuild.yaml prefixed with _ (e.g. _DB_HOST). Values are set in the Cloud Build Trigger and injected at build time, avoiding hardcoded environment-specific values in source code.
Cloud Build
VPC Virtual Private Cloud
An isolated virtual network within GCP. Cloud SQL and the VPC connector live in the default VPC. Resources in the same VPC can communicate using private IPs without going through the public internet.
Networking
VITE_API_URL
A build-time environment variable injected into the React/Vite frontend during the Docker build. Points to the live backend Cloud Run URL. Baked into the compiled JavaScript — cannot be changed without rebuilding the image.
Frontend
